# AES102 — Suffix/Prefix Policy

## What the rule checks

AES102 (rule code `AES102`, checker `SuffixPolicyChecker` in the `naming-rules` crate) enforces per-layer suffix policy:

- Each file's suffix must match its layer's allowed suffix set (strict policy layers).
- Forbidden suffixes are always enforced regardless of policy.
- Cross-layer validation: a suffix belonging to another layer triggers a mismatch finding.
- Barrel files and entry points are exempt.

## Common violation causes

- File carries a suffix belonging to a different layer (cross-layer mismatch).
- File's suffix is not in its layer's allowed list under strict policy.
- File uses a forbidden suffix.
- File moved between layers without renaming its suffix to match the new layer.

## How to fix (concrete steps)

1. Detect the file's layer from its folder/role prefix.
2. Consult that layer's allowed suffix set and forbidden suffix set.
3. Rename the file to use an allowed suffix for its layer, or move the file to the layer whose domain owns its current suffix.
4. Update imports/references to the renamed file.
5. Re-run `lint-arwaky-cli scan .` and confirm AES102 no longer fires on that file.

## Example

Before (violates AES102 — `agent` suffix used in the `capabilities` layer):
```
crates/calc/src/capabilities_calculator_agent.py
```

After:
```
crates/calc/src/capabilities_calculator_checker.py
```

## Verify

```bash
lint-arwaky-cli scan --filter AES102
# Confirm no AES102 finding remains for the renamed file.
```
